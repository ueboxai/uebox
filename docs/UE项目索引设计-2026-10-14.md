# UE 项目索引设计

> 状态：设计稿，未动代码 · 2026-10-14

## 一句话

盒子替每个 UE 项目在本地记一本「项目档案」：资产、蓝图里有什么、项目自己的 C++ 类和函数、两边谁连着谁。编辑器开着时实时跟着改，Agent 查东西先翻档案，开场还能拿到一页项目概览。**不加新页面，Agent 的工具数不变。**

## 为什么要做（大白话）

现在 Agent 像个不认路的新人，每件事都跑去前台（编辑器）现问：

- 搜资产一次最多 500 条，大项目只能一个文件夹一个文件夹地翻。
- 蓝图一次只能打开一个看，问不了「哪些蓝图调用了 `ApplyDamage`」。
- C++ 只有全文 grep，分不清哪个是类、哪个暴露给了蓝图。
- 每次开新会话都从零认识项目，前几轮全花在「先看看有什么」上。

GitHub 上那几个给大型 UE 项目建知识库的开源项目，路子都是**先画一张平面图，再按图找房间**。我们照这个路子做，但有一点比它们强：我们的插件就在编辑器里，资产一变就能知道，不用定期重扫。

## 参考了谁、拿了什么

| 项目 | 拿来的 | 没拿的 |
|---|---|---|
| tumourlove/monolith | 编辑器关着也能查（档案存在盒子这边）；游标分页；结果字段可裁 | 一个领域一个派发工具、几十个动作 —— 对我们太重 |
| elliotttate/unreal-asset-mcp | 一个搜索框认多种问法（`parent:`、`calls:`）；蓝图存全档、贴图网格只存路径和引用 | 离线解析 .uasset —— 我们有活的编辑器，用不着 |
| lusiem/code-atlas | 每次回包有大小上限，超了给游标续读 | 默认就上向量 |
| Codeturion/unreal-api-mcp | 教训：工具描述里不写清「什么时候该用」，模型就不用 | — |
| 通用代码图谱（codebase-memory-mcp、GitNexus） | 自动生成项目概览 | 不认 UE 宏，接不上蓝图；GitNexus 许可证不允许商用 |

共同做法：SQLite + 全文索引、按内容哈希或修改时间做增量更新。这两样我们都已经有了。

## 怎么做

档案分四块，前三块是数据，第四块是给 Agent 看的摘要。

### 1. 资产档：插件实时推，盒子存

- **第一次连上项目**：插件分批从 AssetRegistry 读全部资产（不加载资产，只读注册表里现成的信息），每批 2000 条推给盒子。读的时候按帧限时，编辑器不卡。
- **之后**：插件订阅 AssetRegistry 的「新增 / 删除 / 改名 / 更新」，攒半秒一批推给盒子（用现成的 `evt` 推送通道，`SendEvent` 已经写好但还没人调用）。
- **编辑器关着那段时间的变化**（比如 git pull 了一批资产）：重连时插件发一份「路径 + 文件修改时间」的轻量清单，盒子对比后只补拉变了的那些。
- **每条存什么**：路径、类型、所在文件夹、引用和被引用、注册表标签。蓝图另存父类（注册表里现成的 `ParentClass` / `NativeParentClass` 标签）。贴图、网格、音频这类「哑资产」只存路径、类型和引用，不存全档。

### 2. 蓝图内容档：借 UE 自己的 Find in Blueprints 数据

UE 的「在所有蓝图中查找」不用打开蓝图就能全项目搜，靠的是保存时写进注册表的 `FiBData` 标签，里面有节点、调用的函数、变量、组件、事件。插件把它解出来，只留名字类信息（调了哪些函数、有哪些变量和组件、实现了哪些事件和接口），存进档案。

这样不用加载一个蓝图，就能回答「哪些蓝图调用了 `ApplyDamage`」「哪些蓝图有 `HealthComponent`」。

**风险**：很老的资产可能没有这份数据（UE 会提示需要重新保存）。缺的那些在档案里标「内容未索引」，查询结果里如实告诉 Agent 有 N 个蓝图没覆盖。**要先上真机验证**这份数据在 5.3 到 5.8 之间是否都能读、读起来有多快。

### 3. C++ 档：用反射，不装解析器

开源项目大多用 tree-sitter 解析 C++ 源码，然后自己补正则去认 `UCLASS` 这些宏，结果在 3000 行以上的头文件、只写了 `GENERATED_BODY` 的类上翻车。我们不用走这条路：编辑器加载完项目模块后，**插件直接遍历项目自己模块里的反射信息**，拿到的是引擎认定的结果：

- 类、结构体、枚举，以及继承关系
- 带 `BlueprintCallable`、`BlueprintImplementableEvent` 之类说明符的函数，含参数和 Category
- 带说明符的属性
- 每个类出自哪个头文件（编辑器里的 `ModuleRelativePath` 元数据）
- 所属模块，以及各模块的依赖（读 Build.cs 的结果）

编译完成和 Live Coding 之后重新导一次这些模块。

**覆盖不到的**：没打反射宏的普通 C++ 类，以及函数之间的调用关系。这些继续用现有的 grep。以后真不够用再考虑加解析器，这期不加原生依赖。

### 4. 桥：前三块一对上就有

| 能回答的问题 | 怎么来的 |
|---|---|
| 这个 C++ 类被哪些蓝图继承 | 资产档的父类 × C++ 档的类 |
| 这个 C++ 函数被哪些蓝图调用 | 蓝图内容档的调用 × C++ 档的函数 |
| C++ 里写死了哪些资产路径 | 现有的 `ue_project_path_refs` 扫描结果存进来 |

### 5. 项目概览：开场一页纸

每个会话开始时，按档案**用规则拼**（不用模型写，不会编造），放进系统提示的 `<environment>` 段，紧挨现有的项目名和引擎版本。上限约 1,500 token。内容：

- 模块：项目模块和项目插件，各自的类数量
- 内容目录：顶层文件夹，每个附「蓝图 N / 材质 N / 关卡 N」
- 蓝图家族：按 C++ 父类分组，取前几大（例如「`AEnemyBase` 的子蓝图 37 个」）
- 关卡列表、GameplayTag 的根节点
- 档案的新旧程度，以及蓝图未覆盖的数量

会话中途不改这一段，免得把提示缓存打碎；档案变了，下个会话再生效。

### 存放

- 每个项目一个 SQLite 文件：`userData/project-index/<项目路径哈希>.db`。项目路径用现有的 `projectPathKey` 统一。
- 全文索引沿用 `ftsText.ts` 现成的分词工具（中文按字切、bm25 排序），和资产库、笔记本是同一套。
- 写入沿用资产库的做法：在主进程里分块写、块之间让出时间。better-sqlite3 的连接跨不了线程，所以不开 worker。
- 删掉文件只会丢档案，下次连上会重建，不影响项目本身。

## Agent 那边怎么变

**工具数不变**，改的是三个现有工具里面怎么查：

| 工具 | 改前 | 改后 |
|---|---|---|
| `ue_content_search` | 现问编辑器，最多 500 条，只能翻名字 | 先查档案，没档案时退回现问。加 `cursor` 续读。查询里能写 `parent:AEnemyBase`、`calls:ApplyDamage`、`has:HealthComponent`、`cpp:`（只搜 C++ 类和函数）|
| `ue_content_dependencies` | 每次让编辑器现场走一遍引用 | 查档案里的引用图，上限照旧，加 `cursor` |
| `blueprint_search_nodes` | 搜节点库 | 不变 |

- 回包带 `index_age` 和覆盖情况。档案正在建的时候说明「正在建立，已完成 43%」，同时退回现问，不让 Agent 拿到半截结果却当成全量。
- 写操作（改名、删除、移动）以编辑器的实时状态为准，不信档案。
- `ue_content_search` 是按名字常驻的工具，常驻组预算已经用满。所以工具描述只加一句话：「项目级问题先用这里，`parent:` / `calls:` / `cpp:` 见回包提示」。完整语法放在第一次调用的回包里，以及技能正文里。描述的改动要和别处省下的字节相抵。

## 用户看到什么

**默认什么都不用做。** 连上项目就自动建，不加开关、不加设置页。

| 位置 | 默认可见 | 按需出现（什么时候） |
|---|---|---|
| 顶栏编辑器状态下拉（`EditorStatusMonitor`） | 一行：「项目索引：已就绪 · 12,345 个资产」 | 第一次建的时候：「正在建立索引 43%」；出错时：一行原因加「重建」 |
| 同一个下拉的「更多」 | — | 「重建索引」 |
| 对话里 | 不显示 | Agent 引用档案结果时不另外标注 |

没有新页面、新弹窗、新开关。

## 分期

| 期 | 做什么 | 做完能干什么 |
|---|---|---|
| 一 | 资产档 + 实时更新 + `cursor` + 状态一行 | 大项目搜资产不用手动分文件夹，引用查询变快 |
| 二 | C++ 反射档 + 项目概览 | 开场就认识项目；能搜「暴露给蓝图的函数」 |
| 三 | 蓝图内容档 + 桥 + 查询前缀 | 「谁继承了 / 谁调用了」一问就有 |
| 四（看情况） | 语义搜索：配了嵌入模型才开，和全文结果按 RRF 合并 | 用说法搜（「掉血相关的蓝图」） |

第四期不一定做。旧长期记忆就是栽在依赖向量模型、召回不准上，前三期用下来如果全文加前缀已经够用，就不做。

每期都要找一个**真的大项目**（几十万个资产）走一遍：首次建档要多久、编辑器掉不掉帧、实时更新跟不跟得上批量导入。

## 不在范围内

- 引擎源码 API 索引（unreal-api-mcp 那种），这是另一件事
- 不带反射的 C++ 调用图
- 团队共享档案、云端档案
- 打包后的 cook 产物
- Agent 自己往档案里写备注（那是「经验」的事）

## 未决问题

1. **FiBData 的可读性和速度**：5.3 到 5.8 各版本能不能稳定解析；老资产缺数据的比例大概多少。决定第三期能不能按这个方案做。
2. **首次建档的帧预算**：每帧给插件几毫秒？需要在大项目上实测后再定。
3. **测试用的大项目**：手上有没有几十万资产的项目可以测？没有的话用哪个公开样例代替（City Sample / Lyra 量级不够）。
4. **多个编辑器开同一个项目**：两个连接同时推送时，以谁为准。初步想法是以最后连上的为准。
5. **档案占的磁盘**：几十万资产预计几百 MB。要不要在「更多」里给个大小显示？默认不给。
