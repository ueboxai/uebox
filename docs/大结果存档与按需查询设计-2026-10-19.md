# 大结果存档与按需查询设计

> 状态：第 0–2 步已实现（`core/resultArchive.ts`、`tools/builtin/resultQuery.ts`），第 2 步待真机验收，第 3 步起未动 · 2026-10-19
> 起因：读 [T-Auto/dsh-ops](https://github.com/T-Auto/dsh-ops) 的省 token 做法，挑出最适合我们的一条。

## 一句话

工具一次返回一大张表（蓝图节点、资产列表、关卡里的 Actor），盒子把整张表存进本次会话的档案，**只给模型看一页目录**和一个短编号 `r3`；模型要哪几行、哪几列，再拿编号来查。**界面不变，常驻工具不变，模型多认识一个工具。**

## 为什么要做（大白话）

现在工具返回多少，模型桌上就倒多少，而且**倒上去就不收**：一张 12 万字符的蓝图图表，之后每一轮请求都要原样再带一遍，直到对话压缩把它摘要掉。

拿本机 2,457 个真实会话统计（口径见附录）：

- **工具返回占了全部消息文字的 94.7%。** 用户说的话、模型写的话加起来不到 6%。
- 单次大结果的长尾很重：

| 工具 | 调用次数 | 中位数 | 最大 | 超过 1.6 万字符的次数 |
|---|---:|---:|---:|---:|
| `search_assets` | 368 | 1,611 | 177,843 | 116 |
| `blueprint_get_graph` | 237 | 6,882 | 127,896 | 63 |
| `project_list` | 61 | 12,801 | 100,912 | 25 |
| `ue_get_actor` | 582 | 459 | 155,474 | 24 |
| `ue_content_search` | 867 | 82 | 87,791 | 23 |
| `project_manage` | 198 | 329 | 291,540 | 21 |

这些大结果有个共同点：**都是同一种记录排成的一张表**，而模型通常只用其中几行 —— 从 300 个模板里挑一个、从 247 个资产里找一棵树、在 200 个节点的图里接一根线。

打个比方：现在是把整个仓库的货都搬到桌上再挑。改成**前台给一张货单，要哪件报编号去取**。

### 能省多少

把这几个工具超过 1.6 万字符的结果换成「目录页 + 编号」，按真实会话回放：

- 工具返回在整段对话里的**累计搬运量少 15%**（「累计搬运量」= 每条结果的字数 × 它之后还有几轮请求；没扣对话压缩，所以是上限估计）。
- 其中 `project_list` 5.3%、`search_assets` 3.2%、`blueprint_get_graph` 2.9%、`project_manage` 2.2%。
- 蓝图图表的目录（每个节点只留 id、类、标题、函数名）平均 **160 字符/节点**，完整版是 **661 字符/节点**，约四分之一。

15% 不是全部。另外两个大头不在这次范围里，见「不做什么」。

## 第 0 步：先删重复（不需要新机制）

统计时发现，大结果里有不少是**同一份数据发了两遍**。这些现在就能删，不用等新机制：

| 位置 | 重复了什么 | 实测 |
|---|---|---|
| `ue_content_search`：`searchAssets.ts:195` | `message` 把 `folders` 目录列表又拼成文字写了一遍 | 87,791 字符里两份各 4.4 万 |
| `project_manage`：`projectTool.ts:2490` | `output` 是 `imported_assets` + `spawn_candidates` 的复本 | 29 万字符里 `output` 占 14 万 |
| 资产格式化：`AssetFormatter.ts:184` | 每行同时有 `realPath` 和 `real_path` | 每行 105 字符 × 2 |
| `project_manage` 每行 | `softPath` / `uePath`、`assetClass` / `className` 两两同值 | — |

删之前要逐个确认谁在读：`projectTool.ts:2539` 的注释说 `output` 是「供后续自动化步骤复用」的，界面或别的工具可能读它。如果有人读，就只从**给模型的文本**里去掉，`details` 原样保留。

`blueprint_apply_graph` 的回执也值得单独看：中位数 1,715 字符，p90 是 21,070，最大 65,775，大头是逐节点回的 `nodes`（id → GUID 加引脚）。累计搬运量里它占 9.7%，比读图还多。模型接下来连线需要 id 到 GUID 的对照，但每个节点的引脚要不要全回，得先查清楚再定。

## 方案

### 什么时候存档

一个工具声明自己的结果里**哪个字段是表**（比如 `nodes`、`assets`、`actors`），以及**目录页显示哪几列**。只有声明过的工具参与，第一批是上面那 6 个，外加 `material_get_graph`。

结果序列化后**超过 16,000 字符**才存档，不超过就照旧整份给。

这个数是从数据里挑的：预算定在 8,000、16,000、32,000、50,000 时，省下的比例分别是 16.3%、15.0%、11.8%、9.8%。从 8K 放到 16K 几乎不少省，但被改变的调用少了很多；再往上就开始明显少省。16K 字符大约 4–5K token。全局只有这一个数，不按工具单配。

### 模型先看到什么

```json
{
  "success": true,
  "blueprint_path": "/Game/UI/WBP_Inventory",
  "graph_name": "EventGraph",
  "node_count": 211,
  "archived": {
    "ref": "r3",
    "list": "nodes",
    "rows": 211,
    "shown": "0–98（目录列）",
    "columns": ["id", "class", "title", "write_as", "member_name", "pos_x", "pos_y", "pins", "..."],
    "note": "这是目录，没有引脚。连线、改默认值前用 result_query 按 id 取完整节点。"
  },
  "nodes": [
    { "id": "8F2A…", "class": "K2Node_CallFunction", "title": "打印字符串", "member_name": "PrintString" }
  ]
}
```

规则只有三条：

1. **表以外的字段原样保留**：总数、分页说明、蓝图路径、提示语，这些本来就小。
2. **表换成目录**：只放工具声明的那几列，能塞多少行塞多少，以 16K 为限，并写清是第几到第几行。
3. **明说缺了什么**。`note` 必须讲清这页**不完整**、缺的是哪部分、怎么取。

第 3 条是吸取教训。`getBlueprintGraph.ts` 顶部的注释记着：以前为了省 token **悄悄**删过引脚和类型，结果模型照着残缺的数据猜引脚名，错了也查不出原因。这次不是删，是**收起来并告诉它怎么拿**。dsh-ops 也坚持同一条：「这一页显示完了」和「整份数据是完整的」必须分开报。

### 怎么查：`result_query`

| 参数 | 意思 |
|---|---|
| `ref` | 必填，`r3` 这种编号 |
| `where` | 按字段等值筛：`{"class": "K2Node_DynamicCast"}`；值给数组表示「任一」：`{"id": ["8F2A…", "C01B…"]}` |
| `search` | 在每行所有文字字段里找子串，不分大小写：`"Inventory"` |
| `fields` | 只要哪几列，默认整行 |
| `offset` / `limit` | 翻页 |

返回同样受 16K 上限约束，塞不下就给 `next_offset`。每次返回的开头都带一行**快照说明**：

> 快照：第 12 轮 `blueprint_get_graph` 读取。之后执行过 2 个修改类工具，图可能已变；要改图请重读。

「修改类工具」直接用每个工具已有的 `risk` 标记（`mutating`）来认，这是工具自己声明的事实，不靠猜。

### 蓝图图表怎么配合写图

`blueprint_apply_graph` 本来就支持**只写一部分**：新节点的连线可以用 node_id 接到图里已有的节点上（`applyBlueprintGraph.ts:488-498`）。所以流程是：

1. `blueprint_get_graph` → 目录页：看清图里有什么、在哪；
2. `result_query` 按 id 取要连的那几个节点的完整引脚；
3. `blueprint_apply_graph` 只写新增的那片。

要整图重写（`clear_existing`）的少数情况，模型可以用 `result_query` 分页取全。工具说明要明说：**整图重写前必须先取全**。

### 存在哪、活多久：不新建存储

完整结果本来就落盘了：工具结果消息的 `details` 会随消息一起写进 `agent-v3-sessions/<会话id>.jsonl`（`core/transcriptStore.ts:38-59`，pi 不裁 `details`）。所以存档**就放在这条消息自己身上**：

- 改写后，给模型的 `content` 是目录页；`details.archive` 里放 `{ ref, lists, text }`，`text` 是原本要给模型的那份完整文本（材质这类 `details` 来源不带 `text`，表就在这条消息的 details 里）。
- 存的是给模型的那份（已经过 `describeNodeForModel` 这类整理），不是插件原始回包。
- 盘上总量基本不变：完整文本只是从 `content` 挪进了 `details`。
- `result_query` 按编号在当前 agent 的消息历史里找到那条消息，读 `details.archive`。
- 编号在会话内从 `r1` 递增，越短越省。

这样有三个现成的好处，都不用另写代码：

- **重启以后照样能查**：恢复会话时消息连同 `details` 一起回来。
- **对话压缩以后也能查**：压缩只改发给模型的那份，内存里的完整历史还在（`createAgent.ts` 里 `restoreSearchBeforeFirstRun` 的注释写明读的是压缩前的 `state.messages`）。现在压缩会把早先的大结果摘要掉，细节就没了；存档后，摘要里只要留下 `r3`，模型还能回来取。所以压缩的摘要指令要加一句「保留结果编号」。
- **子 agent 和团队成员**有各自的会话 id（`${parent}:sub-N` / `:mate-<名>`，`createAgent.ts:1192-1194`），开局复制父 agent 的消息（`builtin/task.ts:257-288`）。所以父 agent 的编号它们能直接查；它们自己产生的编号留在自己那边，父 agent 只看汇报，不需要跨过去。会话删除时编号跟着消息一起没了。

### `result_query` 怎么出现

常驻工具的两条字节线都满了：整组常驻 3 万、点名常驻 8.2 万（`toolSearchCatalog.test.ts:303,310`）。所以 `result_query` **不常驻**，自成一个按需组。

**第一次有结果被存档时，自动加载这一组**：存档结果的 `details.toolSearch` 里带上它，和 `search_tools` 加载工具的记录方式一样。重启时 `restore`（`toolSearch.ts:763`）照旧能恢复，模型下一轮就能看到这个工具。从没触发存档的会话一个字节都不多花。

代价是触发存档的会话会多一次工具前缀重写，也就是一次缓存未命中，和平时加载一组工具一样，每个会话最多一次。

### 接在哪

- 统一接在 `createAgent.ts` 的 `afterToolCall` 里（`:1020`）。它本来就在改写工具结果（追加经验提示、清单提醒），而且所有工具都会经过这里，包括适配工具、原生工具、MCP，以及 `read_local_file` 这类直接返回 pi 内容的内置工具。
- 它可以同时返回新的 `content` 和 `details`，pi 按 `afterResult.details ?? result.details` 合并（`pi-agent-core/dist/agent-loop.js:596-612`）。
- 工具在 `unrealBox` 元数据里多一个可选声明：`archive: { list: 'nodes', catalog: ['id','class','title','member_name','write_as'] }`。
- 没声明的工具完全不受影响。

### 给界面的 `details`

`details` 会经 `host/eventBridge.ts:397-408` 发给渲染层，存进 `userData/chat-history`。`adaptV2Tool.ts:215` 注释里说的 localStorage 已经过时了，现在存的是盘上文件。存档后 `details` 多了一份 `archive.text`，发往渲染层时要在 eventBridge 里剔掉，不然聊天记录会多存一份同样大的文字。要先确认哪些界面卡片读这几个工具的 `details`，保证它们读的那部分不变。

## 不做什么

| 不做 | 原因 |
|---|---|
| Python / Shell 输出存档 | `ue_run_python_script` 占累计搬运量 18%，但中位数只有 341 字符，大是因为调用多（3,020 次），不是单次大。存档帮不上，要另想办法。 |
| 「重读时省掉没变的正文」 | dsh-ops 的另一招。实测同参数重读而且内容完全没变的次数很少（`blueprint_get_graph` 237 次里 16 次），而且它的证明规则会和我们的对话压缩打架。先不做。 |
| 跨会话复用 | 那是 [UE 项目索引](UE项目索引设计-2026-10-14.md) 的事。项目索引做出来以后，`search_assets` 这类工具可能直接查索引，存档只管单次结果的快照。 |
| 自动判断「哪个字段是表」 | 不靠结构去猜，只认工具的声明。 |
| 改常驻工具名单或字节线 | 见上文，`result_query` 走按需组。 |

## 风险

| 风险 | 对策 |
|---|---|
| 模型只看目录就去连线，猜引脚名 | 目录里没有引脚，`note` 明说「连线前按 id 取」；猜错的话 `apply_graph` 本来就会整批回滚并报引脚不存在 |
| 拿过期快照改图 | 每次查询的开头都写快照说明和「之后执行过几个修改类工具」 |
| 多一次往返：本来一次读完，现在要读 + 查 | 只影响超过 16K 的结果，也就是长尾；这些结果原本就要跨好几轮带着 |
| 弱模型不会用编号 | 工具说明写一个完整例子；上线后看真实会话里 `result_query` 的调用率，和存档后直接放弃的比例 |

## 名词表

模型需要认识的新名词只有 **2 个**：

| 名词 | 意思 |
|---|---|
| 结果编号（`ref`） | `r3` 这种，指向本会话存起来的某次大结果 |

## 第 1 步实测

用实现本身回放本机真实会话里的结果，统计口径同附录：

| 工具 | 调用 | 触发存档 | 存档的那些结果的字数 | 目录页最大 |
|---|---:|---:|---|---:|
| `search_assets` | 368 | 116 | 5,572,059 → 1,058,288（少 81%） | 15,963 |
| `project_list` | 61 | 25 | 2,521,519 → 399,200（少 84%） | 15,968 |

每一份存档都用 `offset` 逐页翻过一遍，翻回的行数和原表一致。

实现时定下的几处细节：

- 子 agent 开局拿的是父 agent 消息的同一批对象，`details` 跟着过去，所以父 agent 的编号在子 agent 里也查得到。
- 授权过滤之后，池里一个声明了存档的工具都不剩时，就不放 `result_query`（`resolveAgentTools`）。
- 经验记录（`experience`）看的是工具的原始返回，不是目录页。

## 第 2 步实测与改动

| 工具 | 调用 | 触发存档 | 存档的那些结果的字数 | 最大 |
|---|---:|---:|---|---:|
| `blueprint_get_graph` | 237 | 63 | 2,360,858 → 857,352（少 64%） | 16,000 |
| `material_get_graph` | 136 | 5 | 138,072 → 139,121（多 0.8%） | — |

和原设计不同的三处：

- **一份结果可以存多张表。** 大蓝图图里连线也大：212 根连线就有 3.2 万字符，自己就超预算。所以 `nodes` 和 `connections` 都换成目录，按声明顺序分预算（节点先），`result_query` 用 `list` 参数指定查哪张。
- **材质走另一种来源（`source: 'details'`）。** `material_get_graph` 的正文是它自己排好、按字符额度封了顶的文字，不是 JSON 表。所以正文原样给，结尾补一句存档编号，表从 details 里取。这一步不省 token（实测还多 0.8%），换来的是额度外的节点和连线终于取得到：以前那里是死路，全套材质工具没有第二个读图入口。
- 蓝图的存档声明放在 `getBlueprintGraph.ts`（`BLUEPRINT_GRAPH_ARCHIVE`）旁边，注册表只是引用它。

### 材质读图额度：存档时才收小

既然额度外的部分取得到了，`material_get_graph` 在**被存档、且大额度正文加编号放不下时**改用小额度渲染正文：6,500 / 4,500 / 3,000，合计 14,000（`archive.compact`）。这样「正文 + 结尾那句存档编号」落在 16,000 以内：最坏形状实测正文 14,952 字符，`graphArchive.test.ts` 直接断言这一点。

**不存档的地方照旧用原来的大额度**：14,000 / 12,000 / 6,000，合计 32,000。外部 MCP 客户端直接调工具、不经过 `afterToolCall`；按名单授权、手里没有 `result_query` 的会话也不会存档。这些调用方没有第二条路取额度外的部分，所以不能跟着收小。

正文里「还有 N 个没列」的几句改成了条件句：「结尾有存档编号时，用 result_query 取」。两种情况下这句话都成立。

真实会话回放。用同一份代码只换额度对比，因为会话里留下的旧文本出自不同版本，直接比不公平：

| | 大额度 | 小额度 + 编号 |
|---|---:|---:|
| 触发存档的 5 张大材质 | 75,578 | 59,546（少 21%） |
| 全部 97 次调用 | 221,610 | 205,578（少 7%） |

存档不另存文本的情况有两种：`details` 来源；以及 details 里已经有和给模型的一模一样的表（适配工具都是这样）。这时存档只记 `source: 'details'`，`result_query` 直接读 details。
