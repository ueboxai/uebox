# 网络资产库在大库上卡死 / 崩溃：根因与修复（2026-10-14）

> 现象来自一个 54 万资产、跑旧版 asset-server-standalone 的团队库：
> 「正在下载资产 (338000/539004)」三条进度挂着不动然后软件崩掉，重启后又从头下；
> 筛选「音频」直接卡死。

## 一句话

桌面端把**整个资产库当成一张小表**来用：所有读写都在主进程（同时负责界面和 IPC）里
同步执行，同步要把几十万行一次性拉进内存再一口气写完，查询则依赖「规划器碰巧选对索引」。
库小时看不出来；到了几十万行，任何一步变成 O(全库) 就是卡死，内存跟着库涨就是崩溃。
过去的修法是哪条慢补哪条，补一个冒一个。

## 根因清单（按「伤害 × 普遍性」排）

| # | 根因 | 表现 | 修法 |
|---|---|---|---|
| 1 | 全量对账「全拉进内存 → 一个事务写完」 | 内存几 GB，进度停在 70% 后崩；进度最后才落盘，重启从 0 开始 | 分页落盘 + 断点续传；每片写多少行按上一片「写 + 提交」的实测耗时自适应（adaptiveSlice.ts） |
| 2 | 服务端一行坏数据（父文件夹不在）让整轮回滚 | 永远同步不完。实测旧实现跑 54 万行：`FOREIGN KEY constraint failed`，**写进去 0 行** | 对账和增量都只跳过那一行；增量里跳过的登记去按需补（文件夹拉一遍列表、资产按 key 单取） |
| 3 | 对账把「服务端就缺字段」的行塞进缺行缓冲，3 秒后再来一轮对账 | 永远在全量 | 对账不再触发对账；缺行按需单取，不升级成全量 |
| 4 | 旧服务端每次批量导入都要求所有客户端全量（导入不写 change_log） | 有人一导入，所有人重下全库 | 协议缺陷，客户端改不了；让全量足够轻：没变的行不写（实测第二轮 0 行改写） |
| 4b | 服务端变更日志为空时（库是扫描、批量导入建起来的），对完一轮 lastSeq 还是 0，被当成「从没同步过」 | 每次启动、每次重连都全量 | 判据改成「对完过没有」；这种库拉增量时拿条数和服务端核对一次，对不上才全量 |
| 5 | 每次对账整行重写 → 触发器把每行标成「搜索索引要重建」 | 对账后全库重建全文索引；`updated_at` 被刷成同步时刻 | `UPDATE … WHERE 列 IS NOT 新值`，值没变不写 |
| 6 | 带触发器的写语句，语句日志默认落**磁盘临时文件** | 每插一行建一次临时文件，慢 5 倍 | 所有保管库连接 `temp_store = MEMORY`（vaultConnectionPragmas.ts）；几十万行的单条 DELETE 改分块 |
| 7 | 每次提交顺带的 WAL 检查点在主线程上 | 几十万行的库上一次提交几百毫秒到一秒半，切片写入也压不住卡顿 | 检查点挪到查询 worker（每秒一次 PASSIVE）；大批量写入每写 300 ms 停下来异步等它追平一次；主连接自动检查点调到 64 MB 只当兜底，worker 不在了恢复默认 |
| 8 | `isDelete` 单列索引（只有 0/1） | 没统计或统计不准时规划器选它：一页从 0.1 ms 变几秒。仓库里已经在三处用 `INDEXED BY` 单点绕过 | 删掉这个索引，回收站改用部分索引 `WHERE isDelete = 1` |
| 9 | 扩展名筛选 `fileExtension IN … OR ext IN …`，`ext` 没索引 | 点「音频」全表扫，54 万行 5 s，主线程卡死 | 补 `idx_assetData_ext`（有统计时规划器自己会选它，不用再加排序提示） |
| 10 | 列表查询全在主进程同步跑 | 任何慢查询 = 整个软件不响应 | 资产库列表查询挪到 worker 线程；同一列表的新查询作废排着的旧查询；取消不退回主线程重跑 |
| 10b | 默认视图（全部资产按修改时间倒序）没有索引 | 每翻一页都把全表读一遍再排：54 万行热缓存 0.15 s、冷缓存 2 s 以上 | 补 `(updated_at, assetName)` 索引；规划器估不出命中多少行的窄条件（大小、关键词、收藏、日期、类型、子树）给排序列加一元 `+`，不让它沿索引逐行回表 |
| 10c | 刚写完一大批就整表读：还在 WAL 里的页只能一页一次 ReadFile（内存映射只覆盖主库文件） | 对账收尾数「见过的集合」、差集扫描、重算统计各卡主线程秒级 | 整表读之前先等 worker 把 WAL 追平；差集软删也按片提交，片与片之间被实时变更碰过的行不删 |
| 11 | 实时变更一条一个事务 + 一条 IPC | 同事删一个大文件夹，所有客户端几十万次提交 | 攒批写、界面收一条汇总通知；同一条记录的多次变更按 seq 合成后再排序 |
| 12 | 通知封装把 antd 的 `key` 丢了 | 39 处「先 loading 再用同一个 key 改状态」全部失效；进度条堆成三条永不消失 | 带 key 原样交给 antd；同屏上限改由封装自己管（antd 的 maxCount 满了会借走 key） |
| 13 | `start()` 失败时 `emit('error')` 没人监听 → 原地抛出 | 一次超时之后客户端不重连，直到重启 | 有监听才 emit，照常排期重连；重连成功的也补上定时校验 |
| 14 | 两份保管库建表清单各自漂移 | 索引对不上；新加的部分索引排在补列之前，新建保管库直接失败 | 建表 → 补列 → 索引只在 vaultSchema.ts 一处，测试真的建一遍空库和老库 |
| 15 | `js-flags` 追加两次，后一次覆盖前一次 | `--max-old-space-size` 从没生效；dev 脚本给 16 GB 堆，正式包没有，dev 测不出 OOM | 合成一个开关，并写明它管不到主进程 |

四个反面教训：

- 给 `ANALYZE` 设 `analysis_limit` 采样提速，会把 `isDelete` 这类低基数列估成「很有筛选力」
  （实测从每值 2 万行估成 1001 行），规划器挑错索引，查询慢 900 倍。
- 主连接干脆关掉自动检查点、全交给 worker 定期做：WAL 只有「全部抄完之后的下一次写」
  才从头复用，主线程连续写的时候 worker 永远差最后一点 —— 54 万行对账 WAL 长到 **7 GB**。
  所以写的一方要隔一会儿停下来等 worker 追平（异步等，不占主线程）；实测提交 p99 从
  640 ms 降到 60 ms，WAL 稳定在几十 MB，总吞吐反而比默认的「提交时顺带检查点」高。
- 评审修复时以为「分页先排 id 之后，没有时间索引也不慢」，把它删了 —— 默认视图每一页都在
  付整表排序。索引的去留要按查询形状定：宽条件沿排序索引走最快，窄条件最慢，而规划器
  分不出没有索引的条件是宽是窄，所以窄条件由拼 SQL 的一方显式关掉排序索引。
- 把资产库搜索框改走全文索引：全文索引按词前缀匹配、不拆驼峰，「Character」搜不到
  BP_PlayerCharacter，回收站里按名字搜永远是空的（索引里没有删掉的行）。搜索框保留 LIKE
  子串匹配，慢的问题交给 worker。

## 长时间操作期间「世界还在变」

全量对账要跑好几分钟，第一版只考虑了「拉下来、写进去」，代码审查逐条复现出一串
「期间发生了什么」的问题。现在的规则（SyncClient.runReconcile 文件头有完整说明）：

- 对账开始之后**任何**写进本地的行（用户自己改的、实时推来的）都记成「这一轮见过」：
  差集不会把它当「服务端没有」软删；它所在的快照页晚到时也不再拿旧值盖它。
- 差集只扫这一轮**开始时**本地已有的行；之后才进来的不可能在这一轮的快照里。
- 断点只在「之后没吃进更新的变更」时才续；每一轮结尾都从快照点补一次增量（不管谁触发的）。
- 大批增量分片写入期间，实时变更先攒着；拉取写入时跳过已经被实时变更接上的部分；
  lastSeq 只在接得上时推进，有空档就发一次增量拉取补上。

## 实测（`scripts/bench/network-vault-scale.ts`，54 万资产 / 3000 文件夹）

开发机上测的，**机器当时被别的任务占满、这台机器每次小块写盘要 ~400 µs**（常见机器 5~20 µs，
疑似安全软件的过滤驱动），墙钟只能看量级，以客户现场实测为准。

| 项目 | 修复前（v1.0.8） | 修复后 |
|---|---|---|
| 首次全量对账 | 下载阶段堆内存 877 MB；写入时外键失败，整轮回滚，**写进去 0 行** | 写入 538 999 行，5 行坏数据跳过；峰值堆 77 MB、RSS 199 MB |
| 对账期间 WAL | —（一个大事务） | 稳定在 37 MB（只交给 worker 定期检查点时长到 7 GB） |
| 对账期间主线程 | 一个事务写全部 | 写入按实测耗时切片；收尾整表读之前先等 WAL 追平（这一步之前测到的最长卡顿 1.2 s，来源是读 WAL 里的页和重算统计，修复后没再在这台忙机器上复测） |
| 数据没变时再对账一轮 | 54 万行全部重写、全部标记重建搜索索引 | 改写 0 行，标记 0 行 |
| 中途断掉再启动 | 从 0 开始 | 从断点（第 216 000 行）接着拉 |
| 不筛选按修改时间倒序 / 翻到第 100 页 | 整表排序 | 0 ms |
| 筛选「音频」 | 5 078 ms | 0 ms |
| 窄条件（大小、关键词、收藏、日期）按时间排 | 整表排序 | 110~270 ms（整表读一遍再排，在 worker 里，不卡界面） |
| 升级后首次打开建新索引（一次性） | — | 空闲机器约 2~3 s，忙机器实测到 20 s 以上 |

复测：

```bash
node node_modules/jiti/lib/jiti-cli.mjs scripts/bench/network-vault-scale.ts -- --legacy
```

数据放在 %LOCALAPPDATA%，不放系统临时目录（杀毒软件对临时目录的每次读写盯得格外紧，
测出来偏悲观几十倍）；客户端连接和应用一样由另一个线程做检查点、对账每写一段等它追平一次；
主线程卡顿看「主线程最长一次卡顿」（事件循环延迟），偏高时看紧跟着打出来的「慢调用」
（单次超过 100 ms 的语句 / 事务，带主线程 CPU 时间 —— 机器忙时墙钟会把被抢走的 CPU 也算进去）。

## 还没修的同类问题（按严重度）

都是「代价随全库增长、在主进程同步执行或把全库搬进内存」：

1. **Ctrl+A / 定位资产把结果翻到底**：`AssetManagement/index.vue` 的 `ensureFilesLoaded` 一页页加载直到没有，
   每页 OFFSET 重查 + 整个列表复制进响应式数组；收藏状态批量查询把所有 key 塞进一个 `IN`，超过约 3.2 万个报错。
2. **递归取整棵子树的整行**：`db:assetData:getByFolderKeyRecursive` 不分页，导入到项目弹窗一打开就调用，
   在 ALL 上就是几十万整行过 IPC。
3. **拖动文件夹**（`dragMoveService.ts`）取整棵子树的整行只为数个数、拿 key。
4. **依赖图「被谁引用」**：`instr()` 扫全部行的 `imports`，约 7 s。
5. **批量上传缩略图**：每张图一次不限条数的名称 LIKE 全表扫。
6. **服务端角色的扫描**（本机当服务器时）：切库就全盘扫描并把全部路径读进两个 Set，新文件逐条自动提交。
7. **浏览单个大文件夹按时间排**：没有 `(folderKey, isDelete, updated_at)` 索引，每页整夹排序。
8. 助手的「资产库概况」九个全表聚合。
9. 服务端有、本地存不下的行只记在日志里，界面上看不到「有 N 个资产没同步下来」。
10. **首次全量对账的吞吐**：assetData 上二十几个索引，键随机的那几个每插一行各弄脏一页，
    一行约 11 页；WAL 一页两次写调用。每次小块写盘贵的机器（这台 ~400 µs）上，54 万行首次
    对账要二十几分钟（界面不卡，可续传）。下一步是首次对账「先灌数据、后建索引」放到 worker 里，
    或者新后端直接下发库文件快照。

根上的方向：

- **查询都过 worker**：这次只挪了资产库列表这一条，上面 2、3、4 都该走同一个 worker，写入留在主进程。
- **列表协议改成游标分页**，不再 OFFSET；「全选」改成「按条件全选」，不把行搬到界面。
- **服务端协议**：批量导入写 change_log，别再逼全员全量。旧服务端只修严重问题，这条留给新后端。
- **按客户规模做回归**：`scripts/bench/network-vault-scale.ts` 动过同步或查询路径就跑一次。
