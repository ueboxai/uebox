# 团队选模型与履历设计（2026-10-08）

**状态**：设计稿第一版。一期、二期已实现（2026-10-08），和设计的出入见第 10、11 节。代码位置按 2026-10-08 的 `main` 核对。
接在 [AI 游戏工作室设计](AI游戏工作室设计-2026-09-25.md) 4.1 节「给队员选模型档位」后面，替换那里「强 / 标准 / 快三档」的设想。

---

## 0. 结论先行

**一句话：谁招人，谁配模型；配得对不对，看干出来的活。**

- 用户不知道制作人会招哪些人，所以不让用户按人指定模型。制作人招人时，从用户已配好的模型里挑，并写一句理由。
- 每件活都记下是哪个模型干的、结果怎样。这份**履历**是以后换人的依据，不靠模型自荐，不靠公开榜单。
- 不做问答式面试。只做一次「入职体检」，确认模型在用户这里能正常干活；能力靠试用和真活来看。
- 用户默认什么都不用做。想管的时候，按意图说（「干活的省着点」「审核换一家」），或者点队员旁边的模型标签直接换。

## 1. 打个比方

真实公司怎么用人：

| 公司里 | 盒子里 |
|---|---|
| 岗位（关卡策划、审核） | 队员：人设、职责、记忆。由制作人设立 |
| 员工 | 用户配好的每个模型 |
| 简历 | 模型目录里的事实：哪一家、能不能看图、上下文多长、价格 |
| 入职体检 | 配模型时自动测一次：通不通、能不能调工具、能不能看图 |
| 试用期 | 新模型先分一件小的、能验证的活 |
| 比稿 | 同一件活让两三个模型各做一版，用户挑 |
| 绩效 | 履历：审核结论、用户打回、用户挑中 |
| 调岗 | 换一个模型坐这个岗位，岗位记忆压缩成交接纪要 |

和真实公司不同的一点：**不面试**。公司面试是因为试用一个月太贵，只能聊一小时来猜。模型反过来：问答它最擅长，说得好不代表干得好；让它真干一件小活却很便宜，也准得多。

## 2. 为什么不让用户按人配模型

最直接的做法是「策划用 Claude、执行用 DeepSeek、审核用 GPT」，在界面上给每个人选。这条路走不通：

- **用户不知道会有哪些人。** 队员是制作人看活现场招的，名字和岗位都是它当场起的（工作室设计第 0 节：岗位交给模型）。开工前没有名单可以配。
- **等名单出来再配就晚了。** 第一件活已经用默认模型干了。
- **用户知道的是意图，不是名单。** 「便宜点」「审核别跟干活的同一家」这种话用户说得出来；「第三个队员用哪个模型」说不出来。

所以决定放在信息最全的地方：制作人招人那一刻，知道这个岗位要干什么、要多强、量多大。

## 3. 目标与非目标

**目标**
- 不同队员能用不同厂商、不同档次的模型。
- 用户零操作也能得到一个搭配合理的团队。
- 每个模型选择看得见、有理由、改得动。
- 积累「在这个用户的项目里，哪个模型干什么靠谱」的证据。

**非目标**
- 不做按人配模型的设置页，不做角色模板。
- 不做问答面试，不做模型互评，不自建跑分。
- 不给模型打一个综合分数。履历只记事实。
- 不按阈值自动换人（比如「打回超过 30% 就换」）。换人由制作人提出、说明理由。
- 不做按任务自动路由模型。

## 4. 用户旅程

1. **开工**。用户只说目标，比如「做一个跳台关卡」，不提模型。
2. **招人时配好**。制作人招人时挑模型，回话里一句话说明：
   - 「已招入 关卡策划（Claude Opus：要拆需求做设计）」
   - 「已招入 搭建员（DeepSeek：活多量大，用便宜的）」
   - 「已招入 审核员（GPT-6：换一家来查，不容易和干活的人犯同样的错）」
3. **看**。团队面板里每个队员名字旁边标着它现在用的模型。
4. **按意图管**。用户说「干活的省着点」「审核别和干活的同一家」「别用 Opus」，制作人调整已有的人，之后招的人也照这个来。
5. **精确改**。点队员的模型标签，弹出输入框里现成的那个模型下拉框。改完从这个队员的下一件活开始生效，正在干的活不打断。
6. **出问题**。某个模型用不了（Key 过期、服务挂了），这个队员先改用制作人的模型继续干，标签提示一下。活不停，不弹窗。
7. **换人**。某个岗位的活总被打回，制作人提出换模型，并说明依据：「搭建员换成 Claude Sonnet：DeepSeek 这三件里有两件被你打回，都卡在蓝图连线。」岗位记忆压缩成交接纪要给新模型。
8. **下次开团队**。制作人招人时能读到履历，开局就比上一次搭配得好。用户说过的偏好由现有的[经验学习](Agent自然进化设计-2026-09-30.md)记住，不另建配置。

## 5. 五个环节

### 5.1 简历：只写事实

每个模型的简历来自模型目录和入职体检：厂商、能不能调工具、能不能看图、上下文长度、价格。

不让模型自己写自荐。模型常常连自己是哪个版本都说不准，更说不准自己在 UE 项目里擅长什么。

制作人招人时，招人工具的说明里列出**用户已配好、通过了入职体检的模型**和它们的简历。只给事实，不写「审核必须用另一家」这类规则，怎么搭由制作人判断。

### 5.2 入职体检：只查能不能上班

不判断能力，只确认这个模型在用户这里能正常干活：

- Key 和地址通不通
- 经过用户的网关后，工具调用还能不能用（有些中转会把它弄坏，这是最常见的坑）
- 说是能看图，是不是真能看
- 有没有频率限制

要用到这个模型时测一次（制作人招人挑中它、用户在任务板上换成它），结果缓存起来写进简历。不在配模型时把整张清单测一遍：一个来源动辄几十个模型，大多数永远不会去当队员。没通过的不让用，并且说清卡在哪一步（「让它调工具，两次都没调」），而不是等队员干到一半才出错。

这一项在团队模式之外也有用：现在配了模型却调不了工具，用户要等 Agent 跑到一半才会发现。

### 5.3 试用：新模型先干小活

新配的模型没有任何履历，制作人永远不会优先挑它。所以制作人可以偶尔分它一件小的、能验证的活。干得好就有了第一条记录，干砸了损失也小。

试用要花钱，频率要克制。用户说「别试新人」就不试。

### 5.4 比稿：用户主动发起

用户说「这个关卡布局让 Claude 和 DeepSeek 各做一版」，两版并排给用户看，用户选中的那版记进它的履历，分量最重。

花两三倍的钱，所以只在用户要求时做，平时不自动比。

### 5.5 履历：每件活记一笔

每件活记下：哪个岗位、岗位类型、哪个模型、结果。结果只记机器能确定的事实：

| 信号 | 分量 | 说明 |
|---|---|---|
| 用户挑中（比稿） | 最重 | 真人亲自选 |
| 用户点「重开」打回 | 重 | 真人判断 |
| 审核员给没给通过 | 参考 | 审核员也会看走眼 |
| 卡住次数、花费、耗时 | 参考 | 量出来的数 |

履历是**给制作人和用户看的证据**，不是自动开关。原因：

- **活的难度不一样。** 难活干砸不等于模型差，所以按岗位类型分开看。
- **样本少。** 一个用户一个月可能只开几次团队，几件活的结果不能当定论。

### 6.1 边界：谁当制作人、模型不够怎么办

**制作人用输入框里选的那个模型。** 这是用户开对话时唯一已经做过、也只有他能做的决定，不新增「制作人模型」这个设置。盒子不替用户挑「最强的」来当制作人：判断不可靠，而且推翻用户的选择会让人摸不着头脑。

团队搭得好不好，最取决于制作人。这一点写进帮助文档，不在界面上反复提醒。

**候选人 = 用户配好的、能调工具、通过了入职体检的对话模型**，制作人自己用的模型也在里面。配了三个、其中两个调不了工具，算一个。

| 候选人数 | 怎么办 |
|---|---|
| 0 | 团队开不了，走现有的「去配置模型」引导 |
| 1 | 全队用这一个，就是今天的行为。招人工具里不出现选模型这一项（没得选就不让制作人想），面板上不显示模型名，也不催用户多配模型 |
| 2 个及以上 | 按本文的做法。同一家的不同档次（比如 Opus、Sonnet、Haiku）也算 |

只有一个模型时，审核员和干活的人是同一个模型，交叉检查会弱一些。但审核员是全新上下文、只读，仍然有用，所以照常工作，不额外提示。

**运行中的变化**

- **用户中途在输入框换了模型**：制作人从下一轮开始换。队员不跟着换，各自保留招人时定下的模型。
- **制作人的模型用不了**：沿用现有逻辑，退回全局默认模型。
- **队员的模型被用户从设置里删掉**：这个队员下一件活改用制作人的模型，标签提示，制作人下次派活时看到这个变化，可以重新挑。
- **老团队里的 `strong` / `fast` 队员**：`strong` 跟着制作人，`fast` 走对话模型，和以前一样，不迁移。

## 7. 已知短板

- **中途换模型。** 队员记得之前所有活。换到另一家时，旧对话里各家特有的内容（思考过程、工具调用 id 格式）由模型接入层（pi-ai 的 `transformMessages`）自动转换，不会出错；但原来那家的提示缓存会失效，换人后第一件活会慢一点、贵一点。
- **看图的活。** 派活时起始消息里带图，沿用全应用的规矩：钉的模型看不了图就换视觉模型兜底。队员干活中途截的图不换模型，看不了图的模型收到的是占位文字，和主对话一样。
- **价格只有官方直连的。** 二期起内置目录带上了 models.dev 的官方标价，但只对直连官方端点的来源显示；经网关、订阅套餐用的模型没有价格，「贵不贵」仍靠制作人的常识。
- **花费可能比现在高。** 制作人可能给某个队员挑一个比它自己更贵的模型。第一版靠理由和标签让用户看得见，不设硬上限（见第 9 节）。

## 8. 分期

| 期 | 内容 | 用户看到的变化 |
|---|---|---|
| 一期 | 队员能钉具体模型；招人工具列出可用模型和简历，制作人招人时挑并写理由；团队面板显示模型标签、可点换；**每件活记下是哪个模型干的** | 队员用上不同模型；面板上能看到、能改 |
| 二期（已完成） | 入职体检（工具调用、看图）；制作人招人时读履历；换人；价格进模型目录。交接纪要不做，理由见第 11 节 | 换人有理由；挑模型、换模型时就知道能不能用 |
| 三期 | 设置里的模型列表显示履历；试用；比稿 | 能看到每个模型在自己项目里的表现 |

一期里的「记下是哪个模型干的」不管后面怎么设计都要做：没有记录，后面看结果换人就没有依据。

## 9. 开放问题

1. **要不要默认「队员不比制作人贵」？** 加上更安全，但会挡住「策划用更强的模型」这种合理搭配。倾向不加，先看真实花费。
2. **（已定，二期）履历跨不跨工程？** 跨：按工程记、跨工程汇总，简历里本工程的单独标出来。原讨论： [经验学习](Agent自然进化设计-2026-09-30.md)第 2 节明确不做跨工程推广：冻结的经验换到新环境几乎失效。模型表现和那里的「坑与解法」不同，更像能力的统计，跨工程应该还有参考价值。倾向按工程记、在用户层面汇总展示，制作人优先看本工程的记录。
3. **（已定，二期）履历存哪？** 用户数据目录 `team-models/track-record.jsonl`。原讨论： 团队的账（名册、任务板、派活记录）在会话目录旁的 `<会话>.team/` 下，跟着会话走，不跟着工程走。履历如果要跨工程汇总，就得放用户数据目录，或者两边都放。
4. **（已定，二期）岗位类型怎么归类？** 招人工具的 `role_type`，给示例词、不写死清单。原讨论： 岗位是制作人现场起名的，没有固定分类。倾向让制作人招人时顺带标一个粗类型（设计 / 搭建 / 审核 / 美术……），类型清单不写死。
5. **只配了 Token Plan 的用户怎么算？** 它对外只给 `uebox-agent`、`uebox-fast` 这类虚拟模型，底层是哪家不暴露，所以「审核换一家」在盒子这边判断不了。可以由网关提供一个审核专用的虚拟模型，底层路由到和 `uebox-agent` 不同的厂商；要不要做，归 Token Plan 那边定。

| 每件活记下是哪个模型干的 | `TeamActivity.model` | `core/team/teamStore.ts` |

和设计的出入：

- **候选名单暂时没有入职体检。** 一期的候选 = 输入框模型下拉框里的那些，去掉明确标了不能调工具的（`teamModelCandidates`）。入职体检在二期。
- **派活记录有上限。** `activity.json` 只留最近 200 条，原来就是给「最近改动」用的。二期做履历时要换成不截断的账，或者另起一份。
- **老名册里没钉模型的队员**照旧按 `strong` / `fast` 走，面板上显示成「跟制作人」「对话模型」，用户点开选一个就钉上了。
- **用户定的模型，制作人技术上仍能改。** 工具说明和回话里写明「用户定的，除非用户开口别改」，不做硬拦：用户在对话里说「把审核换成 X」时，制作人得改得动。

| 制作人看履历 | 招人工具说明里每个候选多一行「在用户项目里：搭建 12 件（被用户打回 2），本工程 5 件」，体检没过的再多一行原因 | `teamModels.ts` 的 `describeCandidates` |
| 换人 | 招人工具说明里一句：某个岗位老被打回，可以同名再招换模型，并跟用户说清依据。不设自动换人的阈值 | `teamTools.ts` |
| 价格 | 同步脚本带上 models.dev 的 `cost`，两项都是 0 的不写（订阅套餐、本地模型写 0，意思是不按 token 计价，不是免费）。简历里只给**来源 id 和地址都和内置目录对得上**的显示官方标价 | `scripts/sync-provider-catalog.mjs`、`ModelConfig.cost`、`teamModels.ts` 的 `attachPrices` |

和设计的出入：

- **交接纪要没做。** 原以为换模型时要剥掉旧对话里各家特有的内容，核对后发现模型接入层（pi-ai 的 `transformMessages`）已经按模型自动转换。另做一份压缩纪要只是省第一件活的 token，提示缓存照样要失效，不值得多一个环节。上下文太长时现有的自动压缩照常工作。
- **看图体检用了关键词判定**：答案里有 red / 红就算看得见。这是给一张已知颜色的图问一个答案确定的问题，判的是「图有没有送到」，不是在纠正模型的判断。
- **「审核员给没给通过」没进履历。** 现在的验收结论是整个团队的，分不到某一个模型头上。要记得等审核员的结论能对上具体某件活。
- **重新同步模型目录**顺带更新了上游这段时间改过的其他模型（用户拍板接受）。
