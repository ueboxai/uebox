# Agent 自然进化设计（2026-09-30）

**状态**：设计稿第二版。一期主进程部分已实现（`src/main/agent-v3/experience/`），界面和任务流评测未做，和设计的出入见第 14 节。代码位置按 2026-09-30 的 `main` 核对。
第二版对照了 2026 年的最新研究，改了四处：怎么记功、怎么验真、经验做成什么形态、怎么评测。改动和依据见第 12 节。

---

## 0. 结论先行

**一句话：Agent 不记聊天，只记“哪一步在引擎里翻过车、后来怎么过的”。这条经验要先在引擎里核实，然后贴在对应的工具上。只有它真的被采纳、而且采纳后比不给它时成得更多，才能留下来。**

用户平时感觉不到这个过程：不弹窗，不问“要不要记”，不加页面。想看的时候，到技能页可以翻到它学了什么，一键就能撤掉。

旧的长期记忆因为下面四个问题下线，新方案逐条对应：

| 旧问题 | 新做法 |
|---|---|
| **垃圾太多** | 只有引擎给出客观结果的事件才能产生经验，聊天内容不产生经验。写入之前，整理员要先到引擎里只读核实一遍，核实不了就不写。数量有上限。 |
| **召回不准** | 不做语义检索。经验按“工具名 + 报错特征”这把钥匙来找，只在这个工具报错时出现，规则是确定的。 |
| **依赖向量模型** | 完全不用向量。经验就是 markdown 文件，匹配只做字符串和结构比较。 |
| **到底有没有用** | 每条经验单独记功：只有被采纳、而且随后成功的那一条才加分。同时随机留出一部分“不给经验”的对照组，拿两组的差值决定去留。上线前要跑完任务流评测，逐题检查有没有变差。 |

## 1. 打个比方

老员工的本事不在一本厚笔记本里，在**贴在工位上的便利贴**上。

- **贴在具体的东西上。** 比如材质编辑器旁边贴着一张：“本项目的母材质参数名要先查。”碰到这个工具才看得到，不用翻整本笔记。
- **贴之前先确认。** 他不会凭印象就贴，会先打开编辑器看一眼这条是不是真的。
- **看的是有没有照做、照做了灵不灵。** 贴着但没人照做的便利贴，不算有用。照做了以后比没贴时出错少，才算数。
- **有的东西不该写便利贴，该直接改工具。** 如果一条规矩是死的，比如“这个参数只能写整数”，最好的办法是让工具自己在出错之前就拦下来，而不是指望人每次都去看便利贴。

旧长期记忆就像那本厚笔记本：什么都往里写，要用的时候靠“语义相似”去翻，常常翻不到想要的那一页。

## 2. 目标与非目标

**目标**
- 同一个工程里，同一个坑不踩第二次。
- 过程不打断用户，不新增页面，不新增设置项。
- 每条经验都能说清出处，能被证伪、回滚、删除。

**非目标**
- 不记用户说了什么，不做用户画像。
- 不做语义检索，不依赖嵌入模型。
- 不做跨工程自动推广。研究显示，冻结的经验换到新环境几乎不再起作用（见第 12 节）。
- 不学“设计品味”这类没有客观对错的东西。
- 权限、审批、删除、安全相关的规则，永远不自动产生。
- 不训练模型参数。经验只以文件和工具规则的形式存在。

## 3. 经验从哪来：只收“有结局的故事”

一条经验由四样东西组成：**场景 + 翻车现象 + 后来怎么过的 + 证据**。

| 信号 | 例子 | 期数 |
|---|---|---|
| **失败后又成功** | 某工具报错，随后同一个工具改了参数就成功了 | 一期 |
| **引擎校验翻转** | `reviewChanges` 查出编译失败，改完之后通过 | 一期 |
| **技能被证伪** | `load_skill` 之后发现技能里的步骤跑不通（走现有的 `ITERATION_NUDGE` 通路） | 一期 |
| **用户事后手改** | Agent 改过的资产，用户在 30 分钟内又保存了一次 | 二期，只作负信号 |
| **撤销和拒绝** | 用户撤销了 Agent 的一步，或拒绝了审批 | 二期，只作负信号 |

用户在对话里明说的约定（比如“贴图都用 T_ 前缀”）另走一条路：写进工程级的“本项目约定”，内容短，每一轮全量带上。

### 3.1 后台整理员：唯一的写者

- **原始账。** 运行时有一条旁路，把原始账记成会话级 JSONL。原始账只包含工具名、参数摘要、报错、结果和经验是否出场，**不含聊天内容**，保留 7 天。
- **什么时候动手。** 会话结束后，也就是 `runObserver` 发出 `released` 之后才开始。以 Idle 优先级运行，一次只跑一个。
- **什么时候不花钱。** 会话里没有翻车，就没有原始账，也就不调用模型，所以大多数会话的成本是零。
- **报错文本当数据，不当指令。** 报错里可能夹带资产名、第三方插件的输出，整理员的提示词要明确把它们当作被分析的材料。
- **只有整理员能写经验目录。** 干活的 Agent 对这个目录只读，由 `pathBoundary` 拒绝它写入。

### 3.2 写入前先验真（第二版新增）

整理员写下一条经验之前，要用只读工具到引擎里核实它说的东西是否成立。比如这条经验说“先调 A 查参数名”，就确认 A 在当前引擎版本里确实存在，而且返回的内容里有那个参数。

- 核实通过，就带着“已验证：日期 + 引擎版本”写入。
- 核实不了（比如编辑器没开），就只留下候选，等下一次编辑器在线时再核实。候选不会出场。
- 研究依据：让整理员在环境里实测之后再用记忆，通过率从 39% 升到 73%，成本还减半（2609.11060）。

## 4. 两种形态：死规矩进工具，活经验进提示（第二版新增）

研究显示，即使把正确的经验放到模型眼前，工具型 Agent 也只有大约一半的时候照做（2609.05441）。所以，能不靠模型自觉的，就不靠。

| 形态 | 什么经验 | 怎么起作用 | 例子 |
|---|---|---|---|
| **调用前预检** | 确定性的：参数格式、路径规范、必须先做某步 | 在 `beforeToolCall` 里匹配参数，命中就拦下这一次，并把原因和正确做法当作结果交给模型。同一组参数第二次发来就放行，防止误拦把路堵死。 | “材质参数名不在这个材质的参数列表里” |
| **报错时提示** | 非确定性的：排查思路、绕法 | 挂在错误结果后面 | “这个编译错误在本工程出现过，上次是先删掉孤立节点” |

预检是由转正的提示经验“升格”来的。整理员发现一条提示经验每次被采纳都成功，而且触发条件能写成参数匹配，就把它升格成预检。升格后同样要按第 6 节记功，误拦多了就降回提示。

预检规则存成声明式数据（工具名 + 参数条件 + 给模型的话），不生成可执行代码。

**给盒子开发者的出口。** 如果某条预检在很多工程里都成立，说明是工具本身该修。这一类只在用户主动导出时才会汇给我们，通过现有的 `agent-complaint` 路径，不会自动上传。

## 5. 召回：只在需要的时候出现

所有规则都是确定性的，不存在“相似度”这种说法。

**钥匙**
- 必填：工具名，精确匹配。
- 可选：报错特征。先把报错文本归一化（去掉路径、数字、GUID），再截取一段固定字符串。

**出场时机**
1. **调用前**：只有预检规则在这里起作用（第 4 节）。
2. **报错时（主路径）**：钥匙匹配上，就在错误结果后面附上经验，最多 3 条。
3. ~~本会话第一次调用时~~：第一版有这个时机，**第二版默认关掉，只在评测里当作一个实验组**。研究显示有选择地注入优于常驻注入（2607.08716）；第一次调用时并不知道会不会出错，注入等于常驻。

**出场时带上元数据**：来源引擎版本、最近一次验证的日期、状态（试用或转正）。研究显示，越强的模型越容易相信“看起来很新”的过期记忆，把元数据摆出来有帮助（2609.01852）。措辞统一为：“这是过去的经验，以引擎这次返回的结果为准。”

## 6. 记功：谁被采纳了、采纳后灵不灵（第二版重写）

第一版的规则是“出场后 5 步内同一工具成功就给 +1”。这条规则有两个问题：

- **陪跑也加分。** 同时出场的 3 条经验会一起加分，研究里把这叫作“记忆奖励陷阱”（RoMeRL，2608.02508）。
- **量到的是基础成功率。** 很多工具重试一次本来就会成功，测出来的是这个，不是经验的功劳。

第二版改成下面三件事。

### 6.1 采纳判定：结构化，不靠猜

每条经验都写一个“期望动作”：下一步应该调用哪个工具，或者改哪个参数。整理员对照原始账判断：

- **采纳了**：出场后，下一次调用符合期望动作。
- **没采纳**：出场了，但模型走了别的路。

只有**被采纳而且随后成功**的那一条加分；被采纳但同一个错误又出现，减分。没被采纳的不加也不减，只记一次“被忽略”。

### 6.2 对照组：随机留 15% 不给

钥匙已经匹配上的触发时机里，随机留出 15% 故意不出示经验，只记下结果。

- **提升 = 出示组的成功率 − 对照组的成功率**，按每一把钥匙分别计算。
- 对照组只会出现在“已经报错”的时刻，不给经验，最多是多走几步排查，不会让操作变得危险。
- 转正的经验仍保留 5% 的对照，用来持续确认它还有效。

### 6.3 去留规则

```
候选 ──验真通过──▶ 试用 ──采纳后成功 ≥3，且提升 > 0──▶ 转正 ──可升格──▶ 预检
                    │                                   │
                    ├── 被采纳却同一个错误复发 ──────────────┤  立即降级
                    ├── 连续被忽略 5 次 ──▶ 交给整理员改写一次，再被忽略就退休
                    └── 提升 ≤ 0 且样本 ≥ 10 ──▶ 退休
引擎版本变化 ──▶ 整理员逐条重新验真；不通过的退休，通过的保留原状态
容量满（每工程 60 条 / 通用层 150 条）──▶ 挤掉提升最低的一条
```

API 事实另走一套，见文末“API 事实和做法经验分开管（2026-10-15 追加）”。

与第一版的区别：

- **失效看证据，不看时间。** 去掉了“60 天没出场就退休”。长期没出场只会在容量满的时候被挤掉。
- **引擎升级时重新验证**，而不是整批降级。
- 阈值是初值，用评测数据来校准。

## 7. 存放与回滚

遵守硬规则 10：内容以磁盘文件为准。

```
<工程>/.uebox/
  skills/                   已有：工程级技能
  experience/               新增
    ue_set_material_parameter.md    按工具分文件：提示经验 + 预检规则
    _conventions.md                 本项目约定（用户明说的，上限 2000 字）
    .ledger.json                    账本：出场/采纳/成功/对照组计数
    .history/                       每次整理的快照，可以一键回滚
```

单条经验：

```markdown
## 材质参数名要用引擎里的真实名字
- 钥匙：ue_set_material_parameter · 报错含 "Parameter not found"
- 做法：先调 ue_get_material_parameters 取真实参数名，别按编辑器显示名猜
- 期望动作：调用 ue_get_material_parameters
- 出处：2026-09-28 会话 a1b2（同参数失败 2 次，改名后成功）
- 已验证：2026-09-28 · UE 5.5
- 状态：试用
```

**每次整理都会写一份新快照**，不直接覆盖。这参照了 Anthropic dreaming 的做法：整理输出新库，原库不动。技能页可以看到“上次整理改了什么”，觉得不对，一键回到上一版。

## 8. 从便利贴到手册：降级为可选（第二版调整）

第一版的设计是“攒够转正经验就自动合成工程级技能”。研究显示，模型自己生成的技能平均效果是负的（−1.3 个百分点），人工精选的才有用，而且精简的（2～3 个模块）比大而全的好（SkillsBench，2602.12670）。

第二版的调整：

- **默认不合成。** 经验以提示和预检两种形态长期存在，这已经够用。
- 同一领域的转正经验攒到 5 条以上，而且技能沉淀开关在 ask 或 auto 档，整理员才**提议**合成一个精简技能。
- 合成出来的技能**先进试用**，在评测里单独跑 A/B，赢了才保留，同时替换掉原来那几条经验；输了就撤掉。

沉淀开关仍然复用现有的三档，不新增设置：

| 档位 | 经验（提示、预检） | 合成技能 |
|---|---|---|
| off | 不学 | 不合成 |
| ask（默认） | 自动长、自动淘汰 | 提议，用户同意后进入试用 |
| auto | 自动长、自动淘汰 | 自动进入试用，在交付里说明 |

## 9. 评测：证明有用，也要证明没害处（第二版重写）

研究的共识是：只比较最后的分数不够。在顺序、交错的任务流里，没有一种方法稳赢（AgentStream，2608.00155）。经验库做得好不好，瓶颈在“候选经验怎么评估和挑选”（EvoPathBench，2609.24663）。

### 9.1 在线：本地计算，不上报

| 指标 | 含义 |
|---|---|
| 每把钥匙的提升 | 出示组与对照组的成功率之差（第 6.2 节） |
| 采纳率 | 经验出场后被采纳的比例，太低说明写得不好 |
| 同坑复发率 | 同一个（工具, 报错特征）在不同会话里重复出现的次数 |
| 撞墙步数 | 每个会话里失败的工具调用数和熔断次数 |
| 预检误拦率 | 预检拦下后，模型坚持原参数重发并且成功的比例 |

### 9.2 上线门槛：离线任务流评测

用 `docs/AI游戏工作室-题库与评分表.md` 的题库，按下面的要求跑：

1. **任务流，不是单题。** 把题目顺序打乱、交错着跑。经验库从空开始，在第 0、1/3、2/3、结束这几个检查点各测一次。
2. **逐题报告变化**，重点列出**变差的题**。研究里精选技能平均能提升 16 个百分点，但 84 道题里仍有 16 道变差（SkillsBench）。
3. **成本一起算**：token 和轮数。经验库让成本膨胀，是已经观察到的失败模式（2608.05778）。
4. **跨工程测试**：在工程 A 攒下的经验，放到工程 B 上跑，检查负迁移。
5. **至少换两个模型**，因为收益受模型能力的影响，而且不是单调的。

**门槛：总分有提升，成本不涨超过 10%，变差的题都有解释，才默认开启。**

### 9.3 实话

- 收益主要在“这个工程特有的坑”和“工具用法上的坑”。
- 预检这种形态的收益最确定，因为它不依赖模型的自觉。
- 对“设计好不好、方案对不对”没有帮助，也不承诺。

## 10. 用户看到什么

**默认可见**
- 基本无感。
- 预检拦下时，工具结果里会写清原因。这是给模型看的，用户在工具卡片里也能看到。

**按需出现**
- 技能页里多一个“本工程经验”分组：
  - 每条显示状态、形态（提示或预检）、采纳次数、提升、出处、最近一次验证。
  - 可以删除、钉住，也可以回滚到上一次整理之前。
- 经验文件放在 `<工程>/.uebox/experience/`，可以直接打开看，也可以随工程进版本库。

**不出现**
- 弹窗。
- 独立的记忆管理页。

**名词计数**

| | 前 | 后 |
|---|---|---|
| 新名词 | — | 1 个：“经验”（“预检”只是经验的一种状态，在详情里显示） |
| 新页面 | — | 0 |
| 新设置项 | — | 0（复用技能沉淀开关） |

命名刻意不用“记忆”：`longTermMemoryRemoved.test.ts` 守着 i18n 和 CHANGELOG 里不能出现那个词。而且这确实是另一种东西，它不记人，只记工具。

## 11. 分期

**一期：最小闭环**
- 原始账：失败后成功的配对、`reviewChanges` 的翻转、经验是否出场。
- 整理员：在 `released` 之后以 Idle 优先级运行；写入前先验真。
- 报错时出场，带上元数据。
- 采纳判定、15% 对照组、去留规则、容量上限、快照和回滚。
- 技能页分组。
- **任务流评测。过了门槛才进入二期。**

**二期：预检和用户纠正信号**
- 提示经验升格为预检。
- 插件推送资产保存、蓝图编译、PIE 起止的事件，和 `writeLedger` 比对，得到负信号。
- 引擎升级时逐条重新验证。

**三期：可选的技能合成**
- 按第 8 节，合成的技能需要单独赢下 A/B 才能保留。

## 12. 第二版改了什么、依据是什么

| 改动 | 第一版 | 第二版 | 依据（2026 年，除注明外均为论文阶段） |
|---|---|---|---|
| 记功 | 出场后 5 步内成功 +1 | 只给被采纳的那条加分，加上 15% 对照组 | RoMeRL [2608.02508](https://arxiv.org/abs/2608.02508) 的记忆奖励陷阱；MemRL [2601.03192](https://arxiv.org/abs/2601.03192) |

### 报错归一化规则怎么定的

从一台开发机最近 400 个会话里抽了真实报错：7084 次工具调用，594 次失败，227 对“失败后又成功”。

- **环境噪声约占 43%，不学。** 包括被中止 135、超时 40、没连上 31、参数没过 schema 17、工具不存在 13、审批 10、会话锁 7，以及网络断开和配额用完。
- **可学的报错里，Python API 用错最多**，例如 `'Character' object has no attribute ...`。其次是蓝图节点或引脚找不到、编译诊断、磁盘只读。
- **归一化规则：**
  - Python traceback 只留最后那行异常；
  - 去掉工具名前缀；
  - GUID 换成 `<id>`，资产路径和磁盘路径换成 `<path>`，数字换成 `<n>`；
  - 属性名、函数名、引脚名原样保留，因为它们就是知识本身。

### 和设计的出入

1. **写入前验真，一期用“本次会话里引擎已经给出成功结果”作为证据。**
   - 用只读工具到引擎里实测留到二期，原因是整理员运行时编辑器常常已经关了。
   - 整理员会拿原始账对账：报错片段必须在原报错里逐字存在；期望动作里的参数必须是成功那次确实改过的；期望动作里的工具必须是这次会话里真的调用过的。对不上就丢弃。
2. **“连续被忽略 5 次”直接退休**，不经过“交给整理员改写一次”这一步。改写放到二期。
3. **经验文件的字段名用英文**（`key` / `advice` / `expect` / `source` / `verified` / `status` / `pinned`），第 7 节的示例是中文字段名，以代码为准。字段名要能稳定解析，界面上显示的是翻译过的标签。
4. **原始账只记引擎工具**（命名空间为 `ue` 或 `ue.*`），不记破坏性操作；子任务的调用写进主会话那一份，整理员按 `agent` 字段分开配对。
5. **同一会话结束多轮时不重复花钱**：原始账里记下“整理到第几条”，下次只看新的。
6. **还没做：** 技能页的“本工程经验”分组，以及任务流评测。

目前没有界面，经验文件直接放在 `<工程>/.uebox/experience/*.md`，可以打开看、手改或删除。

### 两层经验（2026-09-30 追加）

用户提出：很多经验不只针对一个工程。实际抽样看到最多的 Python API 用错一类，就跟着引擎版本走，和具体工程无关。于是经验分成两层，分法照技能系统的分层来。

| 层 | 装什么 | 存在哪 |
|---|---|---|
| **本工程** | 本工程的资产、自己写的类和蓝图、配置、约定 | `<工程>/.uebox/experience/` |
| **通用** | 引擎 API、引擎自带节点、材质设置这类规则 | `<userData>/experience/`（原始账在它下面的 `.trail/`） |

- **召回：** 报错时两层一起查，本工程的排在前面，同一次最多 3 条。
- **放哪层（`curator.ts` 的 `decideLayer`）：** 整理员先提议，再由规则兜底。以下任一情况都放本工程：整理员没说是引擎层、不知道引擎版本、经验文字里提到了本工程的东西（`/Game/` 路径、`BP_` 这类资产前缀、工程名）。只看经验本身的文字，不看参数。Python 脚本几乎总会加载一个 `/Game/` 下的资产，但那和经验里的知识无关。
- **靠证据升级（`promotion.ts`）：** 同一条经验在 2 个以上工程里各自转正，就自动在通用层放一份。这样就算放哪层判错了，也能自己补回来。登记只记工程路径的指纹。
- **适用版本（`runtime.ts` 的 `engineVerdict`）：** 通用经验带 `engines`（验证过的版本）和 `not-for`（不适用的版本）两个字段。
  - 在新版本上照着做并且成功了，就把这个版本加进 `engines`。
  - 在没验证过的版本上照着做了还是同一个错，记进 `not-for`，这个版本上以后不再出场，而且**不扣它的分**，因为这说明版本不适用，不是经验错了。
  - 在验证过的版本上又报同一个错，才按经验错了处理。
- **跨版本出场时如实说明：** 措辞写明“在 UE 5.5 上成立，还没在 5.6 上确认”。
- **容量：** 每个工程最多 60 条，通用层最多 150 条。原来还有“每个工具最多 5 条”，2026-10-15 去掉了，原因见文末。

### 片段具体度（2026-10-01 追加）

之前的短板：片段只要求“原报错里逐字存在、至少 6 个字”，写成 `not found`、`has no attribute` 也能进门，进门后什么报错都能对上。`ue_run_python_script` 跑的是模型现写的代码，同一个工具名下什么报错都有，工具名这把钥匙几乎不起区分作用，这个问题在它身上最严重。

现在的判据在 `specificity.ts`（`patternProblem`）。整理员写入前判一次，召回时拿**新报错**再判一次，后者能兜住手改过的经验，以及这条规则出来之前写下的旧经验。

- **所有工具：**
  - 片段至少 12 个字；
  - 去掉占位符和通用词（error、not、found、object、attribute、failed……以及中文的“失败”“未找到”）后，还得剩下至少一个能起区分作用的词。
- **上帝工具**（`ue_run_python_script`、`ue_run_console_command`）另外要求：
  - Python 工具只学 Python 异常，“执行未确认”“没连上”这类不学。
  - 不学脚本自己的 bug：NameError、SyntaxError、IndentationError、UnboundLocalError、AssertionError 等。那是这一次现写的代码写错了，不是引擎的规矩。
  - 片段必须带引号里的名字，并且覆盖异常信息的一半以上。
  - 片段必须包含报错**在说的那个名字**，即信息里最后一个引号名，跳过带占位符的实例名。比如 `'character' object has no attribute` 带了名字、也够长，但它对角色的任何属性都成立，知识其实在 `'is_hidden'` 上。
- **同会话兄弟报错：** 同一工具在这次会话里还有别的报错（指纹不同），片段如果也能对上它们，说明太宽，直接丢弃。
- **提前省钱：** 上帝工具的报错如果注定学不了（不是异常、或者是脚本 bug），连候选都不进，不花模型调用。
- **噪声名单补充：** “没有连接的虚幻引擎项目”“未收到 Python 完成结果”“Python 执行未确认”加进环境类。

**用真实报错回放：** 本机 400 个会话里 `ue_run_python_script` 的 95 次失败：
- 16 次是环境类；
- 20 次没有 Python 异常行，其中一部分是抽样时把报错截到 300 字造成的，实际原始账保留得更完整；
- 59 次可学。对这 59 次，把异常信息整句当片段，有 52 次能通过；另外 7 次没通过，主要是被截到 120 字后丢了主语名。

### 上帝工具的学法（2026-10-01 追加）

`ue_run_python_script` 和 `ue_run_console_command` 跑的是模型现写的代码，“工具名 + 报错”这把钥匙对它们几乎不起区分作用。好在代码在执行前就能看到。现在分四步学：

1. **换钥匙：从工具名换成 API 名**（`specificity.ts` 的 `symbolOf`）。
   - Python 从报错里认出“类.成员”或“函数(参数)”，比如 `character.is_hidden`、`assetregistry.getassetsbyclass(class_path_name)`。规则照真实报错的几种形状写，认不出就不加这把钥匙。
   - 控制台命令的钥匙取命令名，也就是第一个词。
   - 召回时，新报错说的得是同一个 API。
   - 抽得出 API 钥匙的经验默认进通用层，不等整理员开口。经验文字里提到本工程东西的，照旧留在本工程。
2. **学“改了哪一行”**（`curator.ts` 的 `scriptDiff` 和 `avoidFromDiff`）。
   - 原始账给上帝工具多记一份脚本或命令的全文，上限 2 万字。
   - 整理员看到的是失败那次和成功那次的行级差异，不再是截短的参数。
   - “错误写法”（如 `.is_hidden`）从“失败那次删掉、成功那次没有”的行里确定性地抽出来，不靠模型。
3. **执行前提醒**（`precheck.ts`，挂在 `createAgent` 的 `beforeToolCall` 上，先于审批）。
   - 只用“已验证”的经验：代码里出现错误写法就拦一次，告诉模型怎么改。
   - 同一段代码原样再发就放行；放行后真跑成了，说明拦错了，那条经验降回试用，不再拦。
   - 拦下后模型改了代码并且成了，记一次采纳成功。
4. **到引擎里验真**（`probe.ts`）。
   - Python 经验写入前，如果这个工程的编辑器正连着，就用只读探针（只做 `dir()`）确认旧写法不存在、新写法存在。
   - 引擎否定的不写；确认的在来源里注明“checked in editor”；编辑器没开就照旧以试用身份写入。

**控制台命令：** 插件原来失败时只回一个 `Failed`，工具只能说“执行失败（错误码 500）”，什么都学不到。现在插件（`UAL_SystemCommands.cpp` 的 `Handle_ExecConsole`）失败时会带回原因：
- 有输出就带输出；
- 命令名不存在时报 `Command not recognized: '<命令名>'`；
- 命令存在但不接受这组参数时报 `Command '<命令名>' exists but did not accept these arguments`。

命令名换了的，原来的名字就成了错误写法；只是参数改了，就不拦命令名。

**顺手修的：** UE 的 Python 绑定常抛不带前缀的 `Exception: ...`，以前归一化时认不成 Python 异常。

### API 事实和做法经验分开管（2026-10-15 追加）

**发现的问题：** 用户本机通用层的 `ue_run_python_script.md` 有 8 条，3 条已退休，退休的 3 条一次都没出过场。“每个工具最多 5 条”加上“还没出过场的 0 分、排最前”，实际效果是只留最近 5 条：引擎核实过的“LevelEditorSubsystem 没有 set_level_viewport_camera_info”被一条新来的挤掉了。

**根因：** 两种东西用了一套管法。
- **做法经验**，比如“材质参数名要先查真实名字”：灵不灵说不准，要试用、对照组、按效果去留。原规则对它合适。
- **API 事实**，比如“5.7 里某个类没有某个成员”：问一下引擎就知道真假，在这个版本里一直成立；Python API 有上万个成员，条数本来就没有上限。判据是 Python 经验抽得出 API 钥匙（`specificity.ts` 的 `isApiFact`），确定性的，界面上不多一个概念。

**改了什么：**
- **容量（`admission.ts`）：** 去掉每工具 5 条。防稀释是召回那一侧的事，召回已经按三把钥匙精确对上、一次最多 3 条。只按层限总量，事实（每层 1000）和做法（60 / 150）分开算，互不挤占。API 事实同一个钥匙只留一条：已有的转正或钉住了，新的不放；还在试用，换成新的。
- **淘汰顺序（`lifecycle.ts` 的 `evictionScore`）：** 还没出过场的试用排在“出过场却一次没成”的后面。没出场只说明那个错还没再犯。
- **事实的去留：**
  - 写入时编辑器里核实过，直接已验证；
  - 没核实过的，整理员每次开工时复查几条（`upkeep.ts` 的 `recheckFacts`，一次最多 3 条）；
  - 同一个错又报了一次，本身就证明那个成员不存在，也算已验证；
  - 不留对照组，不因为“照做了又错 / 被忽略 / 提升不够”退休。照做了又报同一个错，恰好再证明了一次。只有引擎说“它其实存在”才退休；通用层在没验证过的版本上被否定，记进 `not-for`。
  - 执行前拦错了，事实不降级，去掉 `avoid`（它只认成员名，换个类可能就是对的写法）。
- **脚本 bug 补一条：** “在 None 上取属性”（`'nonetype' object has no attribute ...`）是前面的查找落空、脚本没判空，不学。
- **退休记原因**（`retired-because` 字段），设置页详情里显示。
- **修旧账（`upkeep.ts` 的 `repairLayer`）：** 别的退休路径都要先有出场记录，所以没原因、账本里一次没出过场的退休经验，只可能是被容量挤掉的，放回来。启动时修通用层，整理员开工时修那个工程。

**仍未做：** 用引擎生成的 `unreal.py` 存根在执行前直接查 `unreal.Xxx.yyy` 这类引用，另起调研。
